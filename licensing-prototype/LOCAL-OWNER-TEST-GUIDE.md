# دليل تشغيل لوحة المالك محليًا — اختبار فقط

> **تنبيه:** هذه نسخة تجريبية غير صالحة للإنتاج أو استقبال مدفوعات أو حسابات عملاء. لا تشغّلها على عنوان شبكة عامة أو خادم Render. لا تستخدم كلمات مرور أو مفاتيح TOTP أو معلومات دفع حقيقية.

## المتطلبات
- Node.js 22 أو أحدث.
- نسخة محلية من مستودع `Dhamani-Pages`.
- لا يتطلب اختبار الواجهة بيانات فواتير أو اتصالًا بقاعدة الإنتاج.

## تشغيل نموذج محلي ببيانات وهمية

من جذر المستودع:

```bash
node licensing-prototype/run-owner-local-demo.mjs
```

يعرض الطرفية عنوان الخادم المحلي وكلمة مرور ورمز TOTP تجريبيين يتم توليدهما مؤقتًا عند كل تشغيل. يتغير رمز TOTP كل 30 ثانية. **لا تشارك هذه القيم ولا تستخدمها للإنتاج.** افتح الرابط الذي يظهر في الطرفية بعد تغيير نهاية المسار من `/owner/dashboard` إلى `/owner/login`. أدخل كلمة المرور التجريبية المطبوعة في الطرفية، ثم رمز TOTP الحالي؛ ستنتقل إلى `/owner/dashboard` بعد المصادقة. عند فتح لوحة الإدارة قبل المصادقة سيظهر رفض الوصول، وهذا سلوك متوقع. لإيقاف الخادم اضغط `Ctrl+C`. لا يربط المشغّل قاعدة PostgreSQL أو تطبيق ضماني الأصلي.

## فحص آلي دون تشغيل خادم
من جذر المستودع:

```bash
node --test licensing-prototype/*.test.mjs
```

تغطي الاختبارات تسجيل الدخول بعاملين، جلسة المالك، CSRF لتسجيل الخروج، رفض Host المزوّر، قراءة الطلبات والتراخيص وسجل العمليات، وعزل الواجهة عن المستخدم غير المصرح له. اختبارات PostgreSQL الفعلية تحتاج قاعدة اختبار منفصلة ومتغير `DHAMANI_TEST_DATABASE_URL`، ويجري تشغيلها في GitHub Actions.

## مسارات الخادم المحلي
يستمع `startLoopbackOwnerLoginServer` على `127.0.0.1` فقط. يجب إنشاء `OwnerLoginPrototype` بمُتحقق TOTP موثوق `totpVerifier` داخل المُنشئ، ومخزن جلسات `OwnerSessionStore`، ومستودع قراءة تجريبي `repository`. يوجد مشغّل اختبار محلي ببيانات وهمية، ولكن لا يوجد برنامج بدء إنتاجي؛ شاشة تسجيل الدخول الحالية تجريبية محلية فقط؛ اختبارات HTTP الآلية هي طريقة التحقق المعتمدة حاليًا.

بعد مصادقة اختبارية ناجحة:
- `GET /owner/dashboard` — واجهة الإدارة المحلية المحمية.
- `GET /owner/dashboard.js` — ملف الواجهة المحمي.
- `GET /owner/orders` و`/owner/licenses` و`/owner/events` — قراءة فقط.
- `GET /owner/session` — يعيد وقت انتهاء الجلسة للمستخدم الموثق فقط؛ تستخدمه الواجهة لإخفاء السجلات عند انتهاء المهلة حتى دون نشاط.
- `GET /owner/csrf` — يصدر رمز CSRF حديثًا لجلسة مالك موثقة؛ يبطل الرمز السابق.
- `POST /owner/logout` — يحتاج Cookie الجلسة ورمز `x-csrf-token` الحالي. زر الخروج في اللوحة يحصل عليه ثم ينهي الجلسة ويعود إلى صفحة الدخول.

## حماية CSRF لجلسات PostgreSQL (تجريبية وغير موصولة)

أُضيفت دالتا `issueCsrf` و`verifyCsrf` إلى `PostgresOwnerSessionRepository`. تصدر الأولى رمزًا عشوائيًا وتحفظ تجزئته فقط، وتستبدل أي رمز سابق؛ والثانية تتحقق من التطابق وصلاحية الجلسة وعدم إلغائها. تشمل اختبارات PostgreSQL الحقيقي تدوير الرمز ورفض القديم ورفض الرموز بعد إلغاء الجلسة أو انتهائها أو خمولها. **تنبيه:** التحقق المنفصل من CSRF ثم الإلغاء ليس معاملة ذرية؛ يلزم عند الربط بخادم HTTP استخدام شرط CSRF داخل تحديث الإلغاء نفسه أو معاملة متسقة لتجنب سباق التحقق والتنفيذ.

## التحقق من جلسات PostgreSQL وإلغاؤها (تجريبي وغير موصول)

أُضيف `postgres/owner-session-repository.mjs` لفحص تجزئة الجلسة وصلاحيتها والتحقق من MFA ومدة الخمول، وتحديث وقت النشاط بصورة ذرية، وإلغاء الجلسة عند الخروج. تشمل الاختبارات على PostgreSQL الحقيقي الجلسة السليمة، وإلغاءها، ورفض الجلسة المنتهية أو الخاملة أو غير المكتملة للمصادقة الثنائية. ما زال خادم الدخول الحالي يستخدم الذاكرة المحلية ولا يستدعي هذا المكوّن؛ قبل التشغيل الحقيقي يلزم ربطه بخادم HTTP والتحقق من الكوكيز وCSRF وأمان الاتصال وإدارة التنظيف الدوري.

## إصدار جلسة المالك ضمن معاملة MFA (تجريبي وغير موصول)

يمكن الآن تمرير `sessionToken` و`sessionExpiresAt` إلى `PostgresOwnerMfaAcceptance.accept` لإدراج **تجزئة** رمز الجلسة فقط في `owner_auth_sessions` داخل المعاملة نفسها مع استهلاك التحدي ومنع إعادة استخدام خطوة TOTP. أُضيفت اختبارات PostgreSQL حقيقية للنجاح والتراجع الكامل عند اصطدام تجزئة الجلسة بسجل موجود. لا يزال التحقق التشفيري من TOTP خارج هذا المكوّن، ولا يستخدم خادم الدخول المحلي هذه الجلسات المخزنة، ولا تُرسل ملفات تعريف الارتباط من هذه الطبقة. يجب دمج التحقق وإصدار الجلسة وقراءة الجلسات وإلغائها وحماية CSRF قبل أي استخدام إنتاجي.

## معاملة MFA الموحدة (نموذج غير موصول)

أُضيف `postgres/owner-mfa-acceptance.mjs` ليجمع داخل معاملة PostgreSQL واحدة قفل تحدي MFA، وتحديث حالة منع إعادة استخدام خطوة TOTP، واستهلاك التحدي. تشمل اختبارات PostgreSQL الفعلية خمسة طلبات متزامنة واختبار تراجع عند رفض إعادة استخدام TOTP. **تحذير:** يفترض النموذج أن رمز TOTP تم التحقق منه تشفيريًا خارج هذا المكوّن؛ لا يستدعيه خادم تسجيل الدخول الحالي، ولا يصدر جلسات، ولا يسجل المحاولات الخاطئة. لا يجوز استدعاؤه مباشرة من طلب HTTP أو اعتباره نظام مصادقة إنتاجيًا حتى تُدمج هذه الإجراءات بأمان.

## منع إعادة استخدام رمز TOTP عبر الخوادم (نموذج غير موصول)

أُضيف `postgres/owner-totp-replay.mjs` لتحديث آخر خطوة TOTP مقبولة لكل مالك عبر تعليمة PostgreSQL ذرية (`INSERT ... ON CONFLICT DO UPDATE ... WHERE`). يجري اختباره بتقديم ثماني طلبات متزامنة على PostgreSQL حقيقي في CI. **لا يُستخدم في تسجيل الدخول الحالي**؛ يلزم قبل الربط ضمان صحة الرمز أولًا، وربط تحديث حالة منع الإعادة باستهلاك تحدي MFA وإنشاء الجلسة داخل معاملة متسقة، وتحديد طريقة التعامل مع فشل المعاملة. ولتجنب تعارض DDL عند بدء ملفات الاختبارات بالتوازي، يهيئ مسار CI مخطط الجداول قبل تشغيلها.

## الاستهلاك الذري لتحديات المصادقة (نموذج غير موصول)

أُضيف `postgres/owner-challenge-repository.mjs` لتنفيذ معاملة PostgreSQL تقفل صف التحدي بـ `SELECT ... FOR UPDATE`، وتتحقق من المالك والانتهاء وعدد المحاولات وحالة الاستهلاك، ثم تسجل وقت الاستهلاك داخل المعاملة نفسها. لا يُستدعى هذا المستودع من خادم الدخول الحالي؛ الاختبارات المضافة تستخدم Pool وهميًا ولا تثبت التزامن الحقيقي في PostgreSQL. **مهم:** عند الربط مستقبلًا يجب التحقق من رمز TOTP وحجز منع إعادة استخدامه ذريًا ضمن معاملة آمنة قبل منح الجلسة، وعدم استهلاك تحدٍ صالح بسبب رمز خاطئ دون تسجيل المحاولة. لا يجوز اعتبار هذا الملف وحده مسار دخول مكتملًا.

## مقترح التخزين المشترك (غير مفعل)

الملف `postgres/003_owner_auth_proposal.sql` يقدم جداول مقترحة لحفظ تجزئات الجلسات وتحديات MFA وتواريخ الانتهاء والإلغاء في PostgreSQL، ولا يتم تشغيله أو ربطه بلوحة المالك الحالية. يتطلب التفعيل لاحقًا عمليات ذرية لاستهلاك التحديات ومنع إعادة استخدام TOTP عبر الخوادم، وتخزينًا آمنًا لأسرار المالك، وتنظيفًا دوريًا للجلسات، واختبارات تزامن فعلية. تم أيضًا توحيد اسم حقل سجل الأحداث في الواجهة مع `action` المعاد من المستودع.

## اختبارات محاولات المصادقة المتزامنة

أُضيفت اختبارات تتأكد من أن إرسال نفس تحدي MFA بالتزامن لا ينشئ أكثر من جلسة واحدة، وأن تكرار الرمز الخاطئ يلغي التحدي بعد خمس محاولات، وأن رمز TOTP المستخدم لا يُقبل مرة أخرى لتحدٍ آخر في الفترة الزمنية نفسها. هذه الاختبارات تعمل على نموذج Node.js داخل عملية واحدة؛ لا تثبت سلامة التزامن بين عدة خوادم أو بعد إعادة التشغيل.

## حد طلبات المصادقة الثنائية المعلقة

يقبل نموذج المالك 20 تحديًا معلقًا كحد أقصى في الذاكرة، ويزيل التحديات المنتهية قبل إصدار تحديات جديدة. عند امتلاء الحد، يرفض طلبات التحدي الجديدة مؤقتًا دون إنشاء جلسة. هذا الحد محلي ومؤقت ولا يُعد بديلًا عن ضبط معدلات الطلبات مركزيًا أو الحماية من الهجمات الموزعة في الإنتاج.

## التعامل مع انتهاء الجلسة

عند رفض واجهة القراءة بسبب انتهاء الجلسة أو إلغائها، تزيل لوحة الإدارة الصفوف المعروضة وتعيد المستخدم إلى `/owner/login`. وتعيد التحقق عند العودة إلى تبويب المتصفح بعد تركه في الخلفية. يُطبق الخادم التجريبي حد خمول قدره عشر دقائق منذ آخر طلب موثق، وتجدد الطلبات الموثقة المهلة حتى انتهاء الجلسة المطلق. تضبط الواجهة أيضًا مؤقتًا محليًا حتى موعد انتهاء الجلسة لإخفاء الصفوف وإعادة التوجيه دون نشاط، وتتحقق من الوقت مجددًا عند العودة للتبويب. قد تتأخر مؤقتات المتصفح في الخلفية، ولا تغني هذه الآلية عن ضبط مهلة الخمول والاختبار على الأجهزة الحقيقية قبل الإنتاج.

## حدود الجاهزية
- لا يوجد HTTPS أو Secure Cookie في الخادم المحلي.
- تخزين الجلسات ورموز TOTP ومحددات محاولات الدخول مؤقت داخل الذاكرة.
- لا توجد لوحة إدارة إنتاجية أو بوابة دفع أو قاعدة بيانات تراخيص إنتاجية موصولة.
- نجاح اختبارات CI لا يعني جاهزية نشر تجاري أو تطبيق iPhone أصلي.

لا تُرفع أي بيانات أو أسرار حقيقية إلى GitHub Pages أو مستودع الاختبار.
