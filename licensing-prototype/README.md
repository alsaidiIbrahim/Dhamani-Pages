# ضماني — نموذج أولي معزول لمحرك التراخيص

**للتجارب فقط؛ غير متصل بتطبيق ضماني ولا يصلح للإنتاج أو تحصيل أموال العملاء.**

ينفذ هذا النموذج: اعتماد الدفع يدويًا، إنشاء رمز تفعيل عشوائي، ربط جهاز واحد، التحقق كل 30 يومًا بشهادة Ed25519، نقل الربط، إيقاف الترخيص، وسجل عمليات داخل الذاكرة.

التجربة: `node --test licensing-prototype/engine.test.mjs` باستخدام Node.js 22 أو أحدث.

القيود الأمنية المتعمدة: لا توجد واجهة شبكة أو لوحة إدارة أو قاعدة بيانات دائمة أو مصادقة مالك أو إثبات حيازة المفتاح الخاص للجهاز. يعتمد النموذج على سلسلة المفتاح العام كما هي، ولا يمنع نسخها؛ لا تستخدمه كنظام تفعيل فعلي. كما أن إبطال شهادة صادرة يحتاج اتصالًا جديدًا، فلا يمكن منع الجهاز القديم من استخدامها خلال مهلة عدم الاتصال. يجب تنفيذ خادم خاص، قاعدة بيانات معاملات، مصادقة قوية، وتخزين مفاتيح الجهاز في Keychain/Keystore قبل البيع.

## إثبات حيازة مفتاح الجهاز (نموذج تجريبي)

أضيفت دالتا `issueChallenge` و`completeChallenge`: يصدر المحرك تحديًا عشوائيًا قصير العمر (120 ثانية) لغرض التفعيل أو التحقق، ويوقّع العميل النص `dhamani-device-proof-v1:<purpose>:<challengeId>:<nonce>` بمفتاح Ed25519 الخاص. يتحقق الخادم من التوقيع بالمفتاح العام المسجل، ويستهلك التحدي مرة واحدة حتى لو فشل التوقيع. هذه الآلية تمنع الاكتفاء بنسخ المفتاح العام، لكنها لا تضمن ربطه بجهاز مادي دون تخزين مفتاح خاص غير قابل للتصدير. **واجهتا `activate` و`verify` القديمتان باقيتان لأغراض الاختبار فقط، وتتجاوزان التحدي؛ يجب إزالتهما من الواجهة العامة قبل الإنتاج.**

## حفظ حالة النموذج التجريبي

أضيف `store.mjs` لحفظ الطلبات والتراخيص وسجل العمليات في ملف JSON بكتابة مؤقتة ثم إعادة تسمية، واستعادة الحالة عند تشغيل محرك جديد. لا يخزن رمز التفعيل الخام، ولا التحديات قصيرة العمر. **هذا ليس مخزن إنتاج:** لا يضمن معاملات متزامنة، ولا يوفر صلاحيات إدارة أو تشفيرًا عند التخزين، وإذا لم يُزوّد المحرك بمفتاح توقيع دائم فسيُنشئ مفتاحًا جديدًا عند إعادة التشغيل، فتفشل الشهادات القديمة. يجب استخدام قاعدة بيانات معاملات (مثل PostgreSQL)، وإدارة مفاتيح توقيع مستقرة ومحمية، ونسخ احتياطية مجرّبة قبل التشغيل التجاري.

## استمرارية مفاتيح التوقيع

يمكن الآن تمرير مفتاح Ed25519 خاص إلى محرك التراخيص عبر `signingPrivateKey`، وتحميله من ملف أسرار خارج المستودع باستخدام `loadSigningKeyFromFile`. يفحص النموذج نوع المفتاح وصلاحيات الملف على أنظمة POSIX. تختبر المجموعة إعادة تشغيل المحرك مع المفتاح نفسه والتحقق من الشهادات السابقة. **لا تضع المفتاح الخاص في GitHub أو ملفات الواجهة أو حزمة الهاتف**؛ الإنتاج يحتاج إدارة أسرار آمنة، وتدوير مفاتيح، وإجراءات نسخ احتياطي واسترداد.

## واجهة HTTP تجريبية محلية

يوفر `server.mjs` دالة `createPrototypeServer({adminToken})` للاستماع **حصريًا على `127.0.0.1` بمنفذ مؤقت**. تتضمن المسارات `POST /orders`، و`POST /admin/approve`، و`POST /admin/transfer-challenge` و`POST /admin/transfer-complete`، و`POST /admin/suspend`، و`POST /challenge`، و`POST /complete`. يتطلب اعتماد الدفع والنقل والإيقاف رأس `x-admin-token` بقيمة سرية قوية؛ مسارات الجهاز تعتمد على رمز التفعيل والتوقيع. أُضيف اختبار تكاملي لرفض الإدارة دون سر، والتفعيل الموقّع، ومنع إعادة استخدام التحدي، والإيقاف.

**لا يُنشر هذا الخادم للعملاء:** يستخدم ذاكرة مؤقتة وسرًا ثابتًا، بلا TLS أو مصادقة إدارية حقيقية أو حماية من التخمين أو سجل معاملات دائم. لا تشغله على عنوان شبكة عام. يجب إضافة قاعدة بيانات معاملات وواجهة مالك محمية وتحديد معدلات الطلبات وربط مفاتيح الأجهزة غير القابلة للتصدير قبل البيع.

## ضوابط إضافية في النموذج المحلي

أُضيف حد أولي يبلغ 60 طلبًا لكل عنوان اتصال خلال 60 ثانية، مع إرجاع رمز HTTP 429 عند تجاوزه، ورسائل أخطاء عامة لا تكشف رموز التفعيل. **هذا ليس نظام منع إساءة استخدام جاهزًا للإنتاج**؛ يحتاج الخادم التجاري إلى حدود موزعة لكل حساب/ترخيص وعنوان IP، ومراقبة، وسياسات إغلاق مؤقت، وحماية أسرار الإدارة عبر TLS ومصادقة متعددة العوامل.

## نقل الترخيص إلى جهاز بديل

أصبح نقل الترخيص عبر الواجهة التجريبية يتطلب موافقة الإدارة **وتوقيع تحدٍّ قصير العمر بالمفتاح الخاص للجهاز الجديد**. لا تُتاح عملية النقل المباشر عبر HTTP. يرفض المحرك إعادة استعمال التحدي، ويرفض التحقق الجديد للجهاز السابق بعد النقل. **ملاحظة:** قد تستمر شهادة الجهاز السابق محليًا حتى نهاية فترة تحققها البالغة 30 يومًا إذا كان غير متصل؛ لا يمكن إبطالها فورًا دون اتصال.
